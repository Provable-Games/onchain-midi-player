name: integrator-guide
description: Add the onchain MIDI player (Provable-Games/onchain-midi-player) to any Starknet NFT whose token_uri is a base64 JSON data URI. Turn the usual one-pass token_uri into base64 pieces, inject one shared gunzip_segment, the combined engine/API player_segment and complete midi_segment data into an NFT-owned document, keep the SVG art safe, decide where the class hash lives (in the NFT or in a small renderer contract), get each token's MIDI and settings from a composer's sound provider with get_sound, handle failures, and test with snforge against the JS reference. Use when integrating the player into an NFT contract, reviewing such an integration, budgeting its gas, or debugging a broken animation_url.
license: Apache-2.0
compatibility: Needs the Scarb and Starknet Foundry versions in the repository's .tool-versions, and Node 22 or later with npm ci in a full clone of https://github.com/Provable-Games/onchain-midi-player for the offline tools.

Use the class through ITinySynthLibraryDispatcher with a pinned class hash. The reference NFTs check engine() == 'tinysynth' and version() == onchain_midi_player::segment_data::VERSION once in their constructors; this rejects older TinySynth classes that lack the compiled fragment ABI. This is reference configuration policy, not a restriction on other composers: choose a class compatible with your own build. It adds no check to token_uri. The class has no storage or constructor. Preserve ISoundProvider and TinySynthSettings independently of document composition.

The NFT owns its JSON/document/art/UI. Call gunzip_segment(), player_segment() and midi_segment(midi, settings); every result is B64(B64(F)) for a complete fragment with len(F) % 9 == 0. The NFT supplies and aligns the animation_url JSON prefix/closing pieces and complete head/body/bootstrap fragments. Direct splicing is recommended; valid consumer decoding/reconstruction/re-encoding is supported and costs more gas. Compile metadata/art encoding into the consumer.

Use one shared loader for all independent providers. The player fragment contains the exact pinned engine and headless API together. Independent libraries use separate gzip blocks; place dependencies before their dependent blocks. The reference waits for OnchainLibraries.ready then OnchainMidiPlayer.ready before binding controls, requiring the whole composition to initialize. An NFT may instead report an unrelated loader failure and await the MIDI API alone, as shown in the layout guide; leave controls for failed dependencies disabled. Invoke play() from a user gesture or authorized media handler, and use pause(), resume(), stop(), getPlayStatus(), onPassStart() and onStateChange() for NFT-owned behavior. Readiness creates no audio/UI. Pass times are AudioContext seconds, including the shared validated outputLatency + baseLatency estimate; startTime can announce a scheduled future pass.

Arbitrary/community art belongs in an encoded img data URI, with complete framing/alignment allowing later scripts and closing HTML. Original art bytes may contain script-like text. Do not inject untrusted supplied SVG into the parent. The metadata image and displayed art can differ.

Controlled inline SVG/SMIL is an NFT opt-in for art the renderer owns and trusts. The Beast assembly accepts `trusted_art: bool`: true selects `trusted_body_segment()` with `data-trusted-art="inline-svg"`, while false uses the isolated-image body. Its bootstrap imports that trusted SVG and binds `mountArtSync` to the outer and every nested timeline. Imported SVG event handlers have page privileges, so the renderer must control the inline bytes and their escaping. Community art must stay on the isolated path. The ordinary preview deliberately uses an encoded image and cannot demonstrate SVG pause/seek; use the trusted reference and browser synchronization probes linked in the development guide.

Use the Beast consumer for NFT-owned anchoring, art sync, media artwork/controls and hidden-page fallback. Optional browser features cannot block ordinary playback. A future p5.js provider would supply its own fragment under the same loader protocol; real p5.js integration is a separate task. Test independent-provider composition with the small fixture provider.
