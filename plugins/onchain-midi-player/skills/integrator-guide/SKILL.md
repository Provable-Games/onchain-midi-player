---
name: integrator-guide
description: Add the onchain MIDI player (Provable-Games/onchain-midi-player) to any Starknet NFT whose token_uri is a base64 JSON data URI. Turn the usual one-pass token_uri into base64 pieces, inject one shared gunzip_segment, the combined engine/API player_segment and complete midi_segment data into an NFT-owned document, keep the SVG art safe, decide where the class hash lives (in the NFT or in a small renderer contract), get each token's MIDI and settings from a composer's sound provider with get_sound, handle failures, and test with snforge against the JS reference. Use when integrating the player into an NFT contract, reviewing such an integration, budgeting its gas, or debugging a broken animation_url.
license: Apache-2.0
compatibility: Needs the Scarb and Starknet Foundry versions in the repository's .tool-versions, and Node 22 or later with npm ci in a full clone of https://github.com/Provable-Games/onchain-midi-player for the offline tools.
---

Use the class through ITinySynthLibraryDispatcher with a pinned class hash, and check engine() == 'tinysynth' when configuring the NFT. The class has no storage or constructor. Preserve ISoundProvider and TinySynthSettings independently of document composition.

The NFT owns its JSON/document/art/UI. Call gunzip_segment(), player_segment() and midi_segment(midi, settings); every result is B64(B64(F)) for a complete fragment with len(F) % 9 == 0. The NFT supplies and aligns the animation_url JSON prefix/closing pieces and complete head/body/bootstrap fragments. Direct splicing is recommended; valid consumer decoding/reconstruction/re-encoding is supported and costs more gas. Compile metadata/art encoding into the consumer.

Use one shared loader for all independent providers. The player fragment contains the exact pinned engine and headless API together. Independent libraries use separate gzip blocks; place dependencies before their dependent blocks. Await OnchainLibraries.ready then OnchainMidiPlayer.ready before binding controls. Invoke play() from a user gesture or authorized media handler, and use pause(), resume(), stop(), getPlayStatus(), onPassStart() and onStateChange() for NFT-owned behavior. Readiness creates no audio/UI. Pass times are AudioContext seconds, including the shared validated outputLatency + baseLatency estimate; startTime can announce a scheduled future pass.

Supplied art belongs in an encoded img data URI, with complete framing/alignment allowing later scripts and closing HTML. Original art bytes may contain script-like text. Do not inject supplied SVG into the parent. The metadata image and displayed art can differ.

Use the Beast consumer for NFT-owned anchoring, art sync, media artwork/controls and hidden-page fallback. Optional browser features cannot block ordinary playback. A future p5.js provider would supply its own fragment under the same loader protocol; real p5.js integration is a separate task. Test independent-provider composition with the small fixture provider.

Read [layout](https://github.com/Provable-Games/onchain-midi-player/blob/main/docs/token-uri-layout.md), [reference assembly](https://github.com/Provable-Games/onchain-midi-player/blob/main/examples/beast_consumer/src/assembly.cairo), [sound provider](https://github.com/Provable-Games/onchain-midi-player/blob/main/docs/sound-provider.md), [gas](https://github.com/Provable-Games/onchain-midi-player/blob/main/docs/gas.md) and [verification](https://github.com/Provable-Games/onchain-midi-player/blob/main/docs/verifying.md). Regenerate JS/Cairo goldens, ABI/manifests, and run the documented Cairo/Node/browser checks. Declaration/deployment/release transactions require separate maintainer authorization.
